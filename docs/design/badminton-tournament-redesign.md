### A. SEO 문제 (가장 크리티컬)

1. **보이는 `<h1>`이 없음.**
   - 진짜 `<h1>`("전국 배드민턴 대회 일정")과 월별 `<h2>`가 **`#bmkSSR`(SSR 폴백) 안에만** 있는데, JS가 켜지면 `.has-js .bmk-ssr{display:none}`으로 숨겨짐.
   - 실제 인터랙티브 UI는 `<div class="bmk-h1">`, `<div class="bmk-eyebrow">` 같은 **가짜(비시맨틱) 헤딩**으로 표시 → JS 실행 크롤러/사용자에게는 문서 개요가 비어 있음.
2. **구조화 데이터 — 상세는 OK, 목록이 얕음.** (예상과 다른 부분, 정정)
   - **대회 상세 페이지**엔 이미 `SportsEvent` JSON-LD가 잘 구현돼 있음 (`contests/models.py`의 `get_jsonld()` L331–418 → name/startDate/endDate/location/organizer/offers/eventStatus). **여기는 잘 되어 있으니 유지·강화만.**
   - **문제는 목록 페이지의 JSON-LD가 얕음.** `ItemList`가 각 항목에 `url`+`name`만 담음 (`preview.html` L26–35). 각 ListItem에 `SportsEvent`(startDate·location 포함)를 **중첩**하면 목록에서도 리치 결과 강화 가능.
   - **목록 카드에 포스터 이미지를 못 씀.** `ContestPreviewView`의 `preview_data`(views.py L199)에 **`first_image`가 빠져 있음** → 재디자인 카드에 대표 포스터를 쓰려면 뷰의 아이템 dict에 이미지 URL을 추가해야 함(디자인과 별개의 백엔드 작업).
3. **페이지 전용 OG 이미지 없음.** 사이트 공통 OG 이미지(1200×630)만 사용 → 공유 시 대회 페이지 정체성 약함.
4. **월별 콘텐츠가 한 페이지에 전부** 임베드(5월 39개·6월 52개·7월 35개…)되어 페이지가 무겁고, 월/지역별 개별 URL(딥링크·색인 타깃)이 없음.

### B. 리스트 탭 오류 (사용자가 말한 "리스트 탭 오류")

`renderDesktopBody()`의 list 분기(651–661줄)에서:

1. **빈 상태(empty state) 가드 없음.** 캘린더 분기에는 "선택한 날짜에 대회가 없어요"가 있지만, 리스트 분기는 결과가 0개여도 **"총 0개 대회" 밑에 빈 화면**만 나옴 → "리스트 탭이 깨졌다"로 보이는 가장 유력한 원인.
2. **다단(column-count:2) + flex 카드 조각화.** 리스트 행은 `column-count:2`인데 각 카드는 `display:flex` → CSS 멀티컬럼이 카드를 컬럼 경계에서 **잘라버려** 시각적으로 깨짐.
3. **월 네비게이션이 리스트 모드에서 오작동.** 리스트는 전체 월을 다 보여주면서도, 상단 월 제목·이전/다음 화살표는 살아 있음 → 화살표를 누르면 **제목(월)만 바뀌고 내용은 그대로** → 혼란.

### C. UI 일관성 문제

1. **데스크톱 카드 vs 모바일 카드가 다른 디자인.** 데스크톱 `rowCard`(날짜 컬럼형) vs 모바일 `timelineCard`(배지 우선형) → 같은 데이터인데 뷰포트마다 딴판.
2. **인라인 스타일 남발.** JS가 만드는 HTML에 `style="..."`이 수십 곳 → 색/여백이 `<style>` 블록과 JS 문자열에 **이중 정의**. 수정 시 두 군데를 다 손대야 함.
3. **세그먼트/필터 스타일 중복** (`.bmk-seg`, `.bmk-fseg`, `.bmk-fseg.fluid`가 거의 같은 토큰 반복).
4. **860px에서 데스크톱/모바일 DOM을 통째로 스왑** → 마크업 이중화, 유지보수·일관성 부담.

### D. 코드 견고성(터지면 전 페이지 백지) 리스크

1. **`#bmkData`가 `|safe`.** 대회 제목에 `</script>` 문자열이 들어오면 데이터 스크립트가 조기 종료 → JSON 파싱 실패 → **IIFE 전체 사망 → 아무것도 안 그려짐.**
2. **`var REGIONS = {{ regions|safe }};`** 이 파이썬 리스트 리터럴을 그대로 방출 → 지역명에 따옴표/개행이 들어오면 JS 문법 오류로 로드 시 사망. (현재 값은 안전하지만 취약.)
3. 죽은 코드: 519–520줄 `dows` 이중 할당(첫 줄은 즉시 덮어써짐) 등 잔재.

### E. 정보구조(현재 카드에 담긴 것)
제목 · 개최일자(예: `2026.05.02(토)~05.03(일)`) · 지역(`[경기]`) · 경기장 · 승급 여부(전국/지역 승급·비승급) · 접수마감일 · D-day 칩. — 정보 자체는 충분. 문제는 **표현의 일관성·SEO·빈 상태 처리.**

### 프롬프트에 대한 보충 메모 (내부용, 붙여넣지 말 것)
- **달력을 버릴지 여부**는 Claude 디자인이 판단하도록 열어뒀습니다. 대회 탐색은 "달력 그리드"보다 **필터 가능한 리스트/그룹 뷰**가 SEO(텍스트 콘텐츠 노출)·모바일 스캔성 양쪽에서 유리합니다. 달력을 남기더라도 리스트를 1차 뷰로 두는 것을 권장.
- **IA(정보구조) 제안**을 프롬프트에 넣은 이유: 현재 모든 월/지역을 한 URL에 쑤셔넣어 색인 타깃이 하나뿐. `/badminton-tournament/서울/`, `?month=2026-05` 같은 크롤 가능한 딥링크가 생기면 롱테일 검색 유입이 크게 늘어남.
- **이미 잘 되어 있어 재활용할 것**(바퀴 재발명 금지):
  - 대회 **상세**엔 `SportsEvent` JSON-LD가 모델 `get_jsonld()`에 완비 → 목록 ItemList의 각 item에 이 구조를 중첩 재사용.
  - 목록 API(`/api/contests/`)는 이미 `region`·`is_qualifying`·`search`·`order`(popular/recent/upcoming)·`schedule_month`·`period`(ongoing/upcoming/past)·페이지네이션을 지원 → 필터 UX 설계 시 이 파라미터에 맞추면 백엔드 추가 최소화. (단 현재 웹 목록은 API가 아니라 SSR 뷰가 데이터를 통째로 내려주는 방식)

- **구현 시 반드시 같이 고칠 것**(디자인과 별개, 백엔드·하드닝):
