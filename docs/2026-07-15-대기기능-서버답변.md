## #1 is_full — ✅ 상세응답은 4모드 모두 판정됨

**결론: 앱이 신뢰하는 상세응답(`GET /api/bands/<bid>/schedules/<sid>/`)의 `is_full`은 4모드를 정확히 판정합니다.** 그대로 신뢰하면 됩니다.

판정 로직 (`BandScheduleDetailSerializer.get_is_full`):
- **제한 없음**: `current_participants >= max_participants`
- **급수별**: 모든 급수 칸(`level_quota`의 각 급수)의 승인자 수가 정원 이상이면 true
- **성별 전용**: 모든 성별 칸(`gender_quota`의 각 성별)이 정원 이상이면 true
- **급수+성별**: 모든 급수×성별 칸이 정원 이상이면 true
- 어느 한 칸이라도 자리 있으면 `false`

즉 `is_full`은 **current>=max가 아니라 "모든 칸이 마감됐는가"** 로 계산됩니다.

### 마감 상태 JSON 예시 (성별 전용, 남1 마감)
```json
{
  "is_full": true,
  "use_level_quota": false,
  "quota_by_gender": true,
  "gender_quota": { "male": 1 },
  "gender_status": { "male_approved": 1, "male_quota": 1, "female_approved": 0, "female_quota": 0 },
  "quota_status": null,
  "max_participants": 1,
  "current_participants": 1
}
```
(검증: 남 1/1 마감 시 `is_full=true` 확인 완료)

### ⚠️ 주의 — 목록 API는 단순 판정
- **목록**(`GET /api/bands/<bid>/schedules/`)의 `is_full`은 `current>=max` **단순 판정**이라 급수/성별 정원에선 부정확할 수 있어요.
- 앱이 "상세응답만 신뢰"한다니 문제없지만, 목록에서 마감 배지를 정확히 쓰려면 별도 요청 주세요(목록 판정도 4모드로 맞출 수 있음).

## #2 대기 취소 — 🔧 버그였음 → 수정 배포 완료

**질문하신 우려가 정확했습니다.** 확인 결과:
- 기존 `POST .../cancel/`은 취소 가능 상태를 `pending`·`approved`로만 봐서, **`waiting`은 `400 "취소할 수 없는 상태입니다."`** 를 반환했습니다. (200 후 안 지우는 게 아니라 아예 400)
- 대기 전용 취소 API는 **없었습니다.**

### 수정 (배포 완료, commit 9077301)
- **`POST /api/bands/<bid>/schedules/<sid>/cancel/`가 이제 `waiting`도 취소**합니다.
  → **앱은 지금처럼 같은 cancel 엔드포인트를 그대로 쓰면 됩니다.** 별도 API 만들 필요 없음.
- 응답: 대기 취소 시 `200 { "message": "대기가 취소되었습니다." }` (참가 취소는 기존 `"참가 신청이 취소되었습니다."`)
- 대기 취소는 `current_participants`를 건드리지 않음(대기는 인원에 미포함).

### 뒷순번 자동 당김 — ✅ 됨
- 대기 순번(`waiting_position`, `my_waiting_position`, `waiting_total`)은 **저장 필드가 아니라 `applied_at` 기준 실시간 계산**입니다.
- 앞 순번이 취소되면 **자동으로 당겨집니다.** (검증: 대기 3명 중 2번 취소 → 3번이 2→1로 당겨짐 확인)
- 앱은 취소 후 상세/내상태를 다시 조회하면 갱신된 순번을 받습니다.
