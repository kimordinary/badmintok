# 앱 전달 — 서버 작업 내용 (2026-08-25, 배포 예정)

> 요약·추측 없이 실제 서버 변경 그대로 기재. 앱(Flutter)에서 붙이거나 동작을 알아야 하는 항목 전부.
> 경로 prefix: 앱 API는 `/api/bands/` (band/api/urls.py 기준).

---

## A. 엔드포인트 (신규/변경)

### A-1. 쪽지 발송 대상 확대 — `pending` 추가 (변경)
- **엔드포인트(기존, 경로 동일)**: `POST /api/bands/<band_id>/schedules/<schedule_id>/notices/`
- **body(변경 없음)**: `{ "message": "<1~500자>", "recipient_user_id": <유저 id> | null }`
- **변경 내용**: `recipient_user_id`로 개별 발송할 때, 수신자 자격 검증이
  `status__in=['approved','waiting']` → **`['approved','waiting','pending']`** 로 확대됨.
  (즉 승인대기=pending=미승인/입금전 에게도 개별 쪽지 발송 가능. rejected·cancelled는 여전히 제외.)
- **전체 발송**(`recipient_user_id` 없음/빈값)은 **변경 없음** — 여전히 `approved`에게만 발송.
- 기존에 pending에게 보내면 오던 `400 "해당 사용자는 일정 참가자/대기자가 아닙니다."` → 이제 정상 발송.
- **앱**: 개별 쪽지 발송 대상 목록에 pending(승인대기) 포함 가능.

### A-2. 참가 대기자 일괄 승인 (신규)
- **엔드포인트**: `POST /api/bands/<band_id>/schedules/<schedule_id>/applications/bulk-approve/`
- **body**: `{ "application_ids": [id1, id2, id3, ...] }`  (승인할 신청 id 배열)
- **동작**:
  - `application_ids` 중 **status='pending'인 것만** 처리. 그 외(approved/rejected/cancelled/waiting/없는 id)는 **에러 없이 무시(스킵)**.
  - **신청 순**(applied_at 오름차순)으로 처리.
  - 각 건마다 **단건 승인(C안)과 동일한 정원 판정** — 4모드(급수별 / 성별 / 급수+성별 / 총원). 정원 이내 → `approved`, 초과 → `waiting`(대기명단 맨 뒤).
  - 승인할 때마다 정원 카운트가 **실시간 누적**되어 다음 건 판정에 반영됨.
- **응답(200)**: `{ "approved": <int>, "waitlisted": <int>, "message": "<str>" }`
  - message 실제 문구:
    - 둘 다: `"{approved}명 승인 (정원 초과 {waitlisted}명 대기명단)"`
    - 승인만: `"{approved}명 승인"`
    - 대기만: `"정원이 차서 {waitlisted}명 대기명단에 배치했어요"`
    - 없음: `"승인할 대기 신청이 없어요"`
- **예외**:
  - 빈 배열 또는 `application_ids` 누락/비배열: `400 {"error": "application_ids(배열)가 필요합니다."}`
  - 종료된 일정(`schedule.is_ended`): `409 {"error": "종료된 일정입니다."}`
  - owner/admin/사이트관리자 아님: `403 {"error": "권한이 없습니다."}`
- **앱**: 응답에 `message`가 항상 포함됨 → 있으면 그대로 표시, 없을 때만 approved/waitlisted로 문구 생성.

### A-3. 자동대진 세션 준비→시작→종료 (변경/신규)
- **MatchSession.status에 `preparing` 값 추가** (기존 `active`, `ended` 에 추가).
- 세션 **생성 시**(앱 start API·콘솔 진입 공통 `create_session_snapshot`) status가 **`preparing`으로 시작**. 이미 존재하는 세션은 `active` 유지.
- **세션 생성(기존)**: `POST /api/bands/match/schedules/<schedule_id>/start/` → 생성된 세션 status=`preparing`.
- **신규 — 운영 시작**: `POST /api/bands/match/<session_id>/begin/`
  - `preparing → active`. 응답: **serialize_session 전체**(아래 D 참고).
  - 종료된 세션이면 `409 {"detail": "종료된 세션입니다. 다시 하려면 리셋하세요."}`
- **운영 종료(기존, 응답 변경)**: `POST /api/bands/match/<session_id>/end/`
  - `active → ended`, `next_lineup=None`. 응답이 **serialize_session 전체로 변경**(과거 `{id,status}` → 이제 전체 상태).
- **preparing 상태 제약**: 경기 생성 계열(fill_court / end_court / edit_match / create_reservation)은 preparing이면
  `409 {"detail": "먼저 [운영 시작]을 눌러 대진을 시작하세요."}` 반환. (출석·코트·설정 변경은 허용)
- **앱 참가자 화면**: my_status의 `session_status`가 `preparing`일 수 있음 → "곧 시작 / 준비중" 표시 필요(아래 A-4).

### A-4. my_status 응답 필드 (변경)
- **엔드포인트(기존)**: `GET /api/bands/match/<session_id>/me/` , `GET /api/bands/match/schedules/<schedule_id>/me/`
- **`session_status`**: 값이 `preparing` | `active` | `ended` (← **preparing 신규 추가**).
- **`current_match`에 `court_name` 필드 추가**:
  - `current_match.court_name`: 코트 이름 문자열, 이름 없으면 `null`.
  - 코트 이름을 콘솔에서 변경하면 이 값에 반영됨.
  - 기존 `current_match.court_index`(int)는 그대로 유지.
  - **앱**: `court_name`이 있으면 그걸 표시(예: "A조 코트"), `null`이면 기존처럼 `court_index`로 "N번 코트".

## B. 서버 동작 변경 (앱 화면에 자동 반영 — 앱 코드 변경 불필요, 규칙만 숙지)

### B-1. 경기수 카운트 / 대기시간 규칙 (변경)
- **경기 종료(end_court)** 시, 경기 시작(started_at) 후 **2분(120초) 미만**이면 참가자 경기수(`games_mixed/mens/womens`)·대기시간(`last_game_ended_at`) **갱신 안 함**.
- **경기 중 인원 교체(edit_match)로 나간 사람**: 그 경기 경기수 카운트 **안 됨**, 대기시간(last_game_ended_at) **그대로 유지**(경기 진입·교체는 대기시간을 리셋하지 않음).
- my_status의 `games`(mixed/mens/womens/total), `playing`(bool), `queue_position`이 서버에서 자동 계산되어 위 규칙대로 반영됨.

### B-2. 성별 미상자 매칭 자격 (변경)
- `SessionParticipant.is_match_eligible()`: 운영자가 세션에서 성별/급수를 덮어쓴(`overridden=True`) 경우, 프로필 원본이 아니라 **그 스냅샷 값으로 매칭 자격 판정**.
- my_status의 `excluded_from_pool`: 프로필 성별이 미상이어도 운영자가 성별을 지정하면 `false`(매칭 포함)로 정확해짐. 앱 표시 로직은 동일.

## C. 앱에서 쓰려면 API 추가 필요 (현재 앱 API에 미노출)

### C-1. 연령대 (age_group)
- `UserProfile`에 **`age_group` property** 추가.
  - 우선순위: **생년월일(birthday, 만나이) → 출생연도(birth_year) → 카카오 age_range** → 없으면 `null`.
  - 반환 형식: `"20대"`, `"30대"` … (문자열) 또는 `null`.
- **현재 노출 범위**: 웹 참가자 명단(schedule_detail.html)에서만 사용. **앱 API(serialize) 어디에도 age_group 필드 없음.**
- **앱에서 연령대 필요 시**: 해당 serialize(예: 참가자 목록/신청자 serialize)에 `age_group` 추가 요청 필요 → 서버에서 필드만 붙이면 됨.

## E. 이전 미커밋 변경 (오늘과 함께 배포됨 — 앱 API 영향)

### E-1. 일정 목록/상세 serializer에 `is_waitlist_full` 필드 추가 (신규 필드)
- 대상: `BandScheduleListSerializer`, `BandScheduleDetailSerializer` (일정 목록·상세 응답).
- 신규 필드 **`is_waitlist_full`** (bool): 참가 정원(급수/성별 정원 반영)이 찼고 **대기 정원(`BandScheduleApplication.WAITLIST_CAPACITY`)까지 모두 찼는지**.
  - `get_is_full(obj)`가 false면 `is_waitlist_full`도 false.
  - 정원 참 + `waiting_count >= WAITLIST_CAPACITY` 이면 true.
- 함께 노출되는 관련 필드(기존): `waiting_count`, `waitlist_capacity`.
- **앱**: 대기까지 꽉 찬 일정을 구분해 "마감(대기 포함)" 표시 가능.

### E-2. `d_day` 계산 로직 변경 (값 의미 변경)
- 대상: 위 두 serializer의 `d_day` SerializerMethodField.
- 종료 판정을 `is_closed or start_datetime < now` → **`obj.is_ended`** 기준으로 변경.
  - `is_ended` = `is_closed`(수동 마감) 또는 **유효 종료시각(effective_end_datetime) < now**.
  - `effective_end_datetime` = end_datetime이 유효하면 그것, 없거나 start보다 이르면(데이터 오류) start로 폴백.
- `'D-Day'` 조건이 `delta == 0` → **`delta <= 0`**: 오늘 시작했지만 아직 안 끝난(진행중) 번개도 'D-Day'로 표시.
- **앱**: `d_day` 값이 "종료"로 바뀌는 시점이 **시작시각이 아니라 종료시각 기준**으로 바뀜. 진행중 번개는 "종료"가 아니라 "D-Day".

### E-3. `BandSchedule` 모델 property 추가 (서버 내부 — 위 판정 근거)
- `BandSchedule.effective_end_datetime` (property): 종료 판정용 유효 종료시각.
- `BandSchedule.is_ended` (property): 종료 여부. (일괄승인 A-2의 409 판정, d_day, 웹 화면 종료표시에 공용 사용)

## D. serialize_session / current_match 필드 구조 (참고 — begin/end 응답)

- `begin_session`·`end_session` 응답은 `serialize_session(session)` 전체.
- `current_match`(my_status 및 코트 내 경기) 필드:
  - `id`, `discipline`("mixed"|"mens"|"womens"), `status`, `started_at`, `team1`[], `team2`[]
  - `court_index`(int), **`court_name`(str|null, 신규)**, `my_team`(1|2, my_status만), `is_coach_court`(bool)
  - team1/team2 원소: `{ participant_id, name, base_level, gender }`
